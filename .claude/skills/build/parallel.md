# Parallel issues

Every issue but an asset slice goes to a `driver` subagent with a context of its own, even when it is the only one in flight, so a long Run never fills one session; the same driver carries the issue from report to report, resumed with SendMessage. Never a fork: a fork carries the main session's whole context into every call of the issue. The main session dispatches every ready issue whose `Touches:` areas are apart from those in flight (step 1), with no fixed cap: the heavy gate steps share a machine-wide pool of slots sized to the CPU (the adapter's `tools/verify/`, `FACTORY_GATE_SLOTS`), so more issues wait for slots rather than slow each other's gates. It keeps Playtest intake, asset slices, the Drift sweep, the retro, the `needs` subagents and every question for the human. A driver makes its Driver's calls itself (SKILL.md) and reports only Human's calls as `escalated`. The main session decides the effort of each driver it dispatches; a driver decides its own Editor rounds' and Verifier checks' (SKILL.md's Agents and effort). The main session itself runs at effort low (the skill's `effort: low`, for the turn `/build` starts; the human starts a Run's session with `claude --effort low` for the turns a report wakes): it relays each `needs` report as `relay.sh` prints it (step 3), and none of its relays is a judgment.

1. **Pick** the open, unblocked `ready-for-agent` issues of the Features the Run works (SKILL.md), in the Spec's order, skipping parked ones, as SKILL.md's Pick step does: save each one's body (the tracker doc's read command) to `<n>.md` in a scratch folder, and run `bash factory/core/touches.sh pick <n>:<its file>...` in that order, with `--busy <n>:<its file>` first for each issue you dispatched whose driver hasn't reported back yet (start.sh may not have saved its issue.md; one named twice holds its areas once). In flight is every issue with a worktree, a parked one's too, since its worktree keeps its files. It prints `#<n>` for each issue whose `Touches:` areas overlap none in flight nor one picked before it (a missing line overlaps nothing), and on stderr why it skips the rest, or that an issue in flight has no issue.md to read its areas from: pass that one as `--busy` and run it again. Claim and dispatch each it prints; the rest wait for the next Pick, after the next landing.
2. **Dispatch** each with the Agent tool (`subagent_type: driver`, `run_in_background: true`), its prompt the lines `factory-issue: <n>` and `factory-spec: <spec>`, plus any decision for it and, when it goes out again, the `factory-note:` lines its earlier drivers reported. Its effort is medium (driver.md's), raised with the Agent tool's `effort` to `high` for a big slice (many files or a Core script, or a rebuild after a red land) and to `xhigh` when it comes back after the same tests failed in two rounds in a row; never `max`. Write the effort first in the prompt, as a line `factory-effort: <level>`. The main session hears as each one ends. A session started before `.claude/agents/driver.md` was installed has no `driver` type: use `subagent_type: general-purpose` with `model: opus` (the Agent tool's name for `claude-opus-5-5`) and the same effort, with that file's body, below its front matter, ahead of the same lines.
3. **On each report**, run `bash factory/core/relay.sh` with the report's `outcome:` line on stdin (a heredoc) and do what it prints, reading nothing else for a relay. It prints one of three things:
   - `relay: agent`, for `needs editor-sonnet`, `needs verifier` or `needs amend-builder <prompt file> <effort>` (every Editor round, the Takeover's too; every Verifier check and brief review; a `Kind: amend` slice's checks, [`amend-slices.md`](amend-slices.md)): make the Agent call it names, with its `subagent_type` and `effort` as printed (the driver decided it; the relay runs `max` at `xhigh` and no effort at `medium`, and says so) and the text below its `prompt:` line, unchanged, as the prompt. When the subagent ends, run the `after:` line it printed, if any (a Verifier check: it compares the workspace, as [`editor.md`](editor.md)'s Subagents says). Then resume that same driver with SendMessage, by the agent id its dispatch returned: the text of every `reply:` line, the relay's then the after's, without `reply: `, then the subagent's final message, unchanged. Don't summarize or judge either: the driver does. Only when it can't be resumed (SendMessage refuses it, or this session didn't dispatch it) dispatch the issue again as step 2, with the same result lines after the prompt's: a fresh driver resumes from its run state. One round or check per report, so this repeats for each.
   - `relay: malformed`: send the driver its `reply:` lines' text with SendMessage, as above; it reports again.
   - `relay: main-session <outcome>`: yours, by that outcome:
     - `landed`: tick `- [x] #<n>` in the Spec (you, never its driver), then pick the next issue.
     - `waits-on <branch>`: its scope overlaps that issue's in an area the Spec's `Touches:` lines missed, since the Pick keeps apart the ones they name. Add a line `factory-note: waited on <branch>: their scopes overlap in an area their Touches: lines don't share; the Spec missed it` to the issue's notes, and dispatch it again once that one lands, the note among its `factory-note:` lines.
     - `escalated`: send the human the push notification, and dispatch anything else that can run. Then ask the human the report's `question:`, with its `option:` lines as the choices (AskUserQuestion). On an answer, mark the issue answered as `docs/agents/issue-tracker.md`'s "How an issue reads" says (comment the answer in the human's words, remove `ready-for-human`, and head the escalation comment's section with the answer), then dispatch the issue again with the answer as a decision line. With no answer the issue stays parked.
       - **A yes to a Lock lift** (SKILL.md's Driver's calls, in any lane: a lift the driver's permission check refused, or one for a test the brief got wrong): the fallback, since `hooks.sh generate` writes an allow rule for `bash factory/core/lock.sh lift` into `.claude/settings.json` (lib/hooks.sh), which a driver subagent's lift runs under without a prompt. Claude Code reads that rule only once it trusts the workspace: in an untrusted folder the lift still prompts. Where a permission prompt or the classifier still refuses it without the human's yes in the session that runs it, run `bash factory/core/lock.sh lift` in the issue's worktree yourself before you dispatch it. If it refuses here too, or `lift` says the issue's one lift is spent, tell the human and leave the issue parked; never work around it. The decision line is then "the human said yes to the lift; the main session lifted the Lock", and its driver does the rest of the step.
     - `needs <what>` for any other subagent (the asset subagent): run it yourself, then resume that driver with SendMessage, its result the subagent's final message.
4. **Land** is one at a time by itself: `land.sh` rebases, and a push refused because the other issue landed first is SKILL.md's rerun.

**Notes:** keep the `factory-note:` lines each report gives. When a note's cause repeats (another note this Feature has, or a cause an earlier retro named), raise its fix with the human at the next dispatch, not at the retro. The fix is an amend, so it waits on their yes: file what they approve on a `factory-improvement` child issue of the **Factory backlog**, as [`retro.md`](retro.md)'s "File it" files one (`Part of #<backlog>` first, its line added to the backlog's `## Open` list), in the shape `docs/agents/issue-tracker.md`'s "How an issue reads" gives, with the notes behind it in its details, for `/factory-amend` to land.

Two Drivers never edit the same files: the Pick keeps apart issues whose `Touches:` areas meet, and, as the backstop for what the areas miss, `brief.sh seal` refuses a scope that may overlap an in-flight issue's (`brief-overlap`), a scope line a later ruling adds included. The Driver's docs (`docs/deviations.md` and `docs/agents/facts.md`) are the exception, since every issue appends to them; a rebase conflict in one is the Driver's to resolve, keeping both sides.
